The problem

The failure mode isn't missed bugs. It's ignored reports.

A conventional scanner flags every place a variable reaches os.system. Most of those are already safe — the value was quoted, or checked against an allowlist, or the branch can never execute, or nothing attacker-controlled reaches it at all.

So the report says 200 findings. Developers read the first 20, learn the tool cries wolf, and the real bug at number 40 ships to production.

Our answer

Split the job in two, and let each half do what it is good at.

  • 1Finding a suspicious path is a mechanical problem. Be exhaustive and deliberately noisy.
  • 2Judging whether it is exploitable is a reasoning problem. Give a model the evidence and make it write down why.

A suppressed finding is never deleted — it stays in the report with its reason, so a reviewer can overrule us and the suppression rate stays measurable.

Architecture · a genuine four-step sequence

Four stages, each owned by one person

Every stage has a written input and output contract, frozen on day one. That is what let seven people build in parallel without blocking each other.

01

Prepare

Source text becomes a Code Property Graph and a language-neutral IR. Two interchangeable engines: the standard-library ast, or Joern.

No build, no pip install, no execution of the code being scanned. 115 nodes in 15 ms; Joern's CPG in ~15 s.

Worked example · one finding, judged twice

The same pattern, two different answers

Both routes below concatenate a query parameter into a shell command. A pattern matcher reports both identically. Only one is a bug.

/ping · app.py:39

  1. 1attacker input enters via HTTP query stringhost = request.args.get("host")
  2. 2value flows into host
  3. 3reaches the dangerous callos.system("ping -c 1 " + host)
Confirmed · CWE-78 · critical

Attacker-controlled HTTP query string reaches os.system() with no validation or sanitisation on the path.

PoC  curl -G http://localhost:5001/ping \
     --data-urlencode 'host=; id'

/safe-ping · app.py:141

  1. 1attacker input enters via HTTP query stringhost = request.args.get("host")
  2. 2passed through shlex.quote()quoted = shlex.quote(host)
  3. 3reaches the dangerous callos.system("ping -c 1 " + quoted)
Suppressed · not exploitable

The value passes through shlex.quote before reaching os.system(), which is the correct defence for OS command injection.

Stage 2 reported this. Stage 3 dismissed it, in writing. That difference is the entire project.

The trap our own QA caught

We first wrote a decoy that ran html.escape() before render_template_string() and labelled it safe. It isn't: html.escape escapes & < > " ' and leaves {{ and }} untouched, so ?name={{7*7}} still executes. A real template injection, mislabelled as a decoy. Logged as QA-001 — a sanitizer only counts if it fits the sink, and that rule is now asserted in the test suite.

Why Joern is the baseline

Joern is a mature CPG analyser with a real inter-procedural data-flow engine — reachableByFlows traces the value across functions itself. It scores 100% recall on both repositories: it misses nothing. What it does not do is judge which of its own findings are exploitable. That gap is the entire contribution.

Beating a data-flow engine is a harder claim than beating regular expressions, which is why Semgrep has been demoted to a secondary row.

Reading this fairly

28 findings across three small files is a demonstration, not a benchmark. We wrote the corpus, and the decoys were chosen to be suppressible, so 100% is a best case. Semgrep is a mature general-purpose tool being judged here on one rule pack against code written to exercise our own engine. The transferable claim is narrower and still worth making: on a corpus with known ground truth, adding a reasoning stage removed every false positive at zero cost to recall — including on top of a real data-flow engine's output. The methodology — label first, then measure — is the part that generalises.

Cross-repository deduplication

The same bug in two languages is one ticket

Findings are fingerprinted on CWE + where the input came from + the shape of the code — never on file paths, function names or variable names, because none of those survive a copy between services.

code_shape() reduces a line to its skeleton: string literals become 0, identifiers become 1. An f-string, a template literal and a + concatenation all reduce to the same thing, because they are the same thing written three ways.

  • →17 confirmed findings become 10 unique patterns
  • →5 patterns appear in more than one service
  • →41% fewer remediation tickets

Workflow

Nothing is fixed without a human saying so

The approval gate

Stage 4 writes a suggested fix for every confirmed finding. apply_fix() refuses to run unless that fix has already been approved — and even then it returns a patch rather than editing the file.

pending → approved → patch handed over
pending → apply · refused

The ordering is enforced in code, not in a process document someone forgets. Every transition records who, when and why. An auto-applied security fix is how you turn one bug into two.

SLA and escalation

Each severity gets a clock. A confirmed finding that outlives its clock breaches and escalates. Applying a fix stops it.

Confirmed findings are pushed into a live DefectDojo over its API — product, engagement, import, then read back to confirm what landed. Each ticket carries the taint path, the verdict and the reproduction steps.

Resilience

The demo does not depend on the venue wifi

If ANTHROPIC_API_KEY is unset, or the call fails, or the reply will not parse, Stage 3 falls back to a deterministic validator that asks the same five questions as rules — and tags the verdict so you always know which one ran.

This is not theoretical. The key in our build environment returned 401 API key is invalid. The engine caught it, fell back, recorded the reason on every verdict, and produced the same 11 confirmed / 6 suppressed. The fallback was proven under a real failure, not a simulated one.

Logged as ENV-1. Every published figure on this page was produced by the offline validator; the Claude path is wired and unit-tested.

Quality

177 tests, and the limitations written down

Test layers

44 unit · 17 end-to-end · 11 accuracy · 26 workflow · 24 integration · 16 API · 15 scenario · 16 requirement

Every test runs offline and deterministically. One test per box on the hackathon slide, and a test that asserts the QA matrix has no row without a test behind it.

The corpus

17 real vulnerabilities across 9 CWE classes, 11 deliberate decoys, and a clean control app where any finding at all is a false positive.

The decoys are what make a suppression rate measurable. Without them there is nothing to suppress.

Bugs we found on ourselves

13 defects logged and closed during the build, including a mislabelled decoy that was really a live template injection, and a fingerprint collision that clustered unrelated findings.

All twenty are in docs/qa-log.md with their resolution.

Known limitations — stated here rather than discovered on stage

  • ·The JavaScript parser is a line scanner, not a real parser. Multi-line call arguments are not handled. Python — the primary target — uses the real ast module and has none of these limits.
  • ·One API call per finding. Correct but slow and costly on a large codebase. Batching is the first thing we would do next.
  • ·Inter-procedural taint is capped at depth 2, resolved by name within a single repository. No cross-file call graph.
  • ·Loop bodies are walked twice, not to a fixpoint. Two passes settle every case in the corpus; it is not proven in general.
  • ·Joern's flow output carries no guard or dead-code information. A separate ast pass recovers both; without it the allowlist and if False: decoys survive validation on the Joern path. That pass is Python-only.
  • ·A Joern scan costs ~15 seconds and ~4 GB of heap on a one-file repository, against ~15 milliseconds for the builtin engine.
  • ·Nothing here has met a 100k-line codebase. The per-finding LLM call would be the first thing to break.

Next

Where this goes after the hackathon

Batch the validation

The Message Batches API cuts both cost and wall-clock time, and removes the single biggest scaling limit.

Joern for JavaScript too

Joern already parses it correctly; wiring it as the default JS front end retires our line scanner and its multi-line gap.

Learn from approvals

A finding a human rejects three times is a rule that needs tuning. Feed the approval queue back into the rule tables.

Incremental scanning

Re-analyse only the functions a diff touched, so the engine can sit in a pull-request check.

Deeper reachability

A cross-file call graph, so http_reachable becomes a proof rather than a heuristic.

More languages

One new builder emits the same IR and the taint engine is unchanged. That was the point of the design.
